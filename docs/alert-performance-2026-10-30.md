# 提醒性能重构与现场验证

2026-10-30，**VibeCoding Go 0.33.0 / build 48**，安装至 /Applications/VibeCoding Go.app。触发问题是提醒出现时操作和视频都卡顿。本轮先确认本机资源压力，再分别修复应用渲染与声音的主线程工作；没有关闭用户的开发任务或其他应用。

## 确认的瓶颈

旧实现给每个显示器创建全屏透明窗口，逐帧在主线程计算路径、构造大量渐变、裁剪并软件重绘。默认光影样式在逻辑 2560×1440、宽度 8 的离屏单帧约 56–71 ms；较宽样式可达 120–465 ms。这些是有限离屏 CPU 渲染测量，不等于屏幕显示帧时间。旧现场 pulse-fragments 的单帧 CPU 绘制约 6–8 ms，同时还有全屏透明合成负担。

声音原路径也会同步读取、合成、校验、写 WAV 并 prepareToPlay。资源压力下曾观察到首次准备约 4–5 秒，原实现会占据主线程。这个时间受当时系统状态影响，不是所有 Mac 的固定音频延迟，也不足以单独解释视频卡顿。

## 架构变化

- 共享一次后台编译的 Metal 光场，沿用 **59 种配方**、原 50 种不同样式、颜色、方向、强度与运动配置。常规提醒不再逐帧生成 Core Graphics 渐变。
- 每个屏幕使用四块不重叠边缘表面，中央不被透明窗口覆盖。当前 5K 背板配置中，实际表面像素降到全屏的 **8.7%–24.9%**，取决于样式的真实光效范围，没有通过降低透明度掩盖性能问题。
- 每个表面最多一帧在途，忙碌时合并/丢弃旧帧，不积压；GPU drawable 等待、编码与提交在 utility 队列，主线程只交付有界参数。仍由一个有限动画时钟控制，目标最高 30 FPS；关闭和替换立即取消，减弱动态保持静态。
- 没有 Metal 时只在后台生成一次静态光效，避免退回持续软件绘制。首次真实后台管线编译约 484 ms；正常启动不强制预热 GPU。
- 声音使用 utility 串行最新请求准备，内置 WAV 直接使用有界缓存 Data，不再重复写临时文件。准备完回主线程播放，关闭、静音、新提醒和退出都会使旧准备结果失效，不在之后突然补播。
- 原有 CLI 光效导出也改为异步 GPU 离屏导出，最多不足 800 万像素、同时一次；普通提醒不触发读回或 PNG 编码。
- 新增 ⌘, 工作台入口，便于从独立对话窗口回到统一面板；原生编辑菜单保持不变。

## 现场样本

使用有限采样脚本读取进程累计 CPU 差分、RSS 和提醒计数，不读取对话正文、代理凭证或公网地址。旧版采到一次自然 pulse-fragments 提醒；新版由工作台“测试完成提醒”触发相同样式的六秒预览。两段都有其他任务和视频，负载并非严格相同，不能当作整机固定加速比例。

| 观察项 | 旧版现场 | 新版现场 |
| --- | --- | --- |
| 提醒期 App CPU 中位数 | 38.08%（5 个采样） | 8.04%（12 个采样） |
| 无提醒 App CPU 中位数 | 6.03% | 1.99% |
| 提醒期 WindowServer CPU 中位数 | 79.72% | 83.91% |
| 边缘窗口 | 1 个全屏 | 4 个边缘 |
| 动画配置目标 | 30 FPS | 30 FPS |

CPU 百分比按单核 100% 计。WindowServer 同时合成整机桌面和视频，这两段没有显示其整体 CPU 降低；不能把 App CPU 改善扩成全系统结果。新版实际四个窗口均为 metal，GPU 完成帧数持续增加，单表面主线程参数交付约 0.002–0.053 ms，关闭后边缘数与动画时钟归零。旧 effect_render_ms 是 CPU draw，新字段是 GPU 执行时间，已显式标注 scope，二者不作同口径比较。

完成提醒的音效实际播放，后台准备约 222 ms；随后输入提醒实际启动音效，准备约 24 ms，sound_prepared_on_main_thread=false、无音频错误。工作台截图只捕获其自身窗口，不作为覆盖于其上的边缘窗口像素证据；光效透明、动画与接缝另用真实 GPU 离屏输出验证。

## 系统资源压力

排查时内置 Data 盘仅约 **110 MiB** 可用，交换空间 **31.7 GB / 32 GB** 已使用；这会放大任何瞬时绘制负载。没有清理用户或其他项目的数据，仅把本项目约 325 MiB 的派生 Swift 缓存移到外置项目 build，并将编译临时目录、模块缓存与随构建执行的隔离测试临时文件固定在外置盘。

迁移缓存的 PCM 包含绝对路径，不能直接在新路径复用，因此后续构建使用全新的 native-module-cache，旧兼容缓存保留。结束前系统盘约 **858 MiB** 可用、交换仍约 **30.5 GB** 使用，资源压力依然存在。本次应用修复不能替代后续系统盘和内存压力处理，也没有证据保证视频在全部并发负载下不丢帧。

## 回归与安装

- **1,022 项 Python 回归通过**；已启用安装的 mise、Hurl、lnav 真实可选引擎检查，无跳过。
- **148 项原生与性能检查通过**，包括 8 项音频准备检查及 6 项 GPU 几何/参数/准入检查。
- **12 项真实 GPU 检查通过**：59 个配方都有可见像素、原 50 种输出互异、预乘透明正确、动画与减弱动态正确、四条带和全幅接缝比较通过（最大分量差 1，无大于 2 的分量差）。
- UI 无变化仍为零列表重建、零行重绘；后台准备与隐藏页面的原有有界回归保持通过。
- 安装后二进制与构建一致，**48 个 Python 源文件全部一致**。升级前 **797 条提醒全部保留**，检查时 798 条；设置、窗口位置、草稿、待续和用量显示配置五项哈希全部未变，Codex 状态 connected。
- 六项网络检测已在新旧安装版各完整点击运行一遍，复制粘贴、输入异常和停止提示也已检查；详见[界面验收](network-ui-2026-10-30.md)。
